# 도메인 — 일일 정산이란 무엇인가 (회계 모르는 분을 위한 가이드)

## 한 줄 요약

> 은행은 매일 새벽, 전날 발생한 모든 거래를 **계좌 단위**와 **회계 계정 단위**로 두 번 집계해서 장부에 기록한다. 이 시스템은 그 자동화 배치다.

## 왜 굳이 매일 집계하는가

은행/카드사/증권사는 거래가 발생하는 즉시 회계 장부에 반영하지 않는다. 이유 세 가지:

1. **트래픽 분산** — 고객 거래는 낮 시간대에 몰린다. 거래 1건마다 회계 장부까지 즉시 갱신하면 트랜잭션 비용이 폭발한다.
2. **회계 무결성** — 회계는 "마감(closing)" 개념이 강하다. 영업일 기준으로 그 날의 거래가 모두 들어왔다는 것을 확정한 뒤, 한 번에 장부에 반영해야 일자별 잔액·손익이 깔끔하다.
3. **실패 회복** — 거래 처리 시스템과 회계 시스템이 분리돼 있으면, 중간에 한쪽이 실패해도 재처리(replay)가 가능하다. 정산 배치가 사실상 그 재처리 지점이다.

## 등장하는 용어

| 용어 | 설명 |
|---|---|
| **거래(transaction)** | 입금/출금/이체/수수료 등 계좌 잔액에 영향을 주는 1건의 사건 |
| **정산(settlement)** | 특정 일자의 거래를 모아 정리하는 과정. 일일/월별/분기별 |
| **분개(journal entry)** | 거래 1건을 회계 장부에 차변/대변 두 줄로 기록한 것 |
| **차변(debit, 借)** | 회계 장부의 왼쪽. 자산 증가, 비용 발생 등 |
| **대변(credit, 貸)** | 회계 장부의 오른쪽. 자산 감소, 부채/수익 발생 등 |
| **복식부기(double-entry)** | 모든 거래를 차변·대변 양쪽에 같은 금액으로 기록하는 방식. 차변 합계 = 대변 합계가 항상 보장된다 |

## 한 거래가 시스템에서 변환되는 흐름

예: 홍길동(110-123-000001)이 ATM에서 5만원 출금.

```
[1단계 — 운영 시스템 (실시간)]
   transactions 테이블에 1행 추가:
     account=110-123-000001, type=WITHDRAWAL, amount=50000, status=COMPLETED

[2단계 — 일일 거래 집계 배치 (Job 1, 새벽)]
   같은 계좌의 그 날 모든 거래를 합산:
     daily_transaction_summaries: account=110-123-000001, date=2026-05-05,
       total_deposit=300000, total_withdrawal=550000, ...

[3단계 — 분개 생성 배치 (Job 2, Job 1 직후)]
   각 거래를 회계 장부 항목으로 변환:
     출금 50000원 거래 →
       journal_entry: 차변 비용계정(현금 출금) 50000
       journal_entry: 대변 자산계정(고객 예금) 50000
   (차변·대변 각각 1행, 합 50000 = 50000으로 균형)

[4단계 — 월별 마감 배치 (Job 3, 매월 1일)]
   한 달치 일일 summary를 다시 합산. 월간 손익/잔액 보고서 토대.
```

## 이 프로젝트가 다루는 범위

본 프로젝트는 위 흐름의 **2~4단계**를 Spring Batch로 자동화한다.

- **Job 1: DailyTransactionAggregationJob** — 일일 거래 집계 (구현 완료, Sprint 01)
- **Job 2: JournalEntryGenerationJob** — 분개 자동 생성 (Sprint 02)
- **Job 3: MonthlyClosingJob** — 월별 마감 (Sprint 03)
- 이들을 매일/매월 자동 트리거하는 **Scheduler** (Sprint 04)

1단계(거래 발생 자체)는 별도의 OLTP 시스템이며, 본 프로젝트에서는 `DataSeeder`로 시뮬레이션한다 (계좌 100개 × 일 1000건 × 7일).

## 의도적으로 다루지 않는 것

이 프로젝트는 학습/포트폴리오 목적이라, 실제 은행 시스템에서 중요하지만 시간 비용이 큰 다음 영역은 의도적으로 단순화/제외했다:

- **잔액 추적**: 일별 opening/closing balance 컬럼은 초기 설계 후 드랍됐다. 정확한 추적은 별도의 일별 잔액 스냅샷 테이블이 필요하며, 이는 정산 집계의 책임 영역이 아니다.
- **거래 카테고리(차변/대변 매핑) 외부화**: Job 2에서 type → 계정코드 매핑을 코드 내부에 둔다. 실제로는 회계 매핑 룰 테이블에서 동적 조회한다.
- **다국 통화/환율**: 모든 금액은 KRW 단일 통화 가정.
- **대사(reconciliation)**: 외부 시스템과의 잔액 일치 검증은 다루지 않는다.
- **승인/마감 워크플로**: 회계팀의 수동 검토/승인 절차 없이 자동 완료.
