## 1. 도메인 — 일일 정산이란 무엇인가

은행은 매일 새벽, 전날 발생한 모든 거래를 **계좌 단위**와 **회계 계정 단위**로 두 번 집계해서 장부에 기록한다. 이를 **일일 정산(daily settlement)** 이라 부른다. 이 시스템은 그 자동화 배치다.

이 문서는 회계가 처음인 독자를 가정하고 용어와 흐름을 차근차근 풀어 둔다. 회계 도메인이 익숙하다면 ["등장하는 용어"](#등장하는-용어)부터 봐도 충분하다.

## 왜 굳이 매일 집계하는가

은행/카드사/증권사는 거래가 발생하는 즉시 회계 장부에 반영하지 않는다. 이유 세 가지:

1. **트래픽 분산** — 고객 거래는 낮 시간대에 몰린다. 거래 1건마다 회계 장부까지 즉시 갱신하면 트랜잭션 비용이 폭발한다.
2. **회계 무결성** — 회계는 "마감(closing)" 개념이 강하다. 영업일 기준으로 그 날의 거래가 모두 들어왔다는 것을 확정한 뒤, 한 번에 장부에 반영해야 일자별 잔액·손익이 깔끔하다.
3. **실패 회복** — 거래 처리 시스템과 회계 시스템이 분리돼 있으면, 중간에 한쪽이 실패해도 재처리(replay)가 가능하다. 정산 배치가 사실상 그 재처리 지점이다.

## 등장하는 용어

| 용어 | 설명 |
|---|---|
| **거래(transaction)** | 입금/출금/이체/수수료 등 계좌 잔액에 영향을 주는 1건의 사건 |
| **정산(settlement)** | 특정 일자의 거래를 모아 정리하는 과정. 일일/월별/분기별 |
| **분개(journal entry)** | 거래 1건을 회계 장부에 차변/대변 두 줄로 기록한 것 |
| **차변(debit, 借)** | 회계 장부의 왼쪽 |
| **대변(credit, 貸)** | 회계 장부의 오른쪽 |
| **복식부기(double-entry)** | 모든 거래를 차변·대변 양쪽에 같은 금액으로 기록하는 방식. 차변 합계 = 대변 합계가 항상 보장된다 |

## 회계의 다섯 가지 계정 종류

회계 장부의 모든 항목은 다음 다섯 종류 중 하나로 분류된다. 이 분류가 정해지면 뒤의 차변·대변 규칙이 자연스럽게 따라온다.

### 잔액 셋: 자산·부채·자본

| 종류 | 정의 | 한 마디 |
|---|---|---|
| **자산 (Asset)** | 보유한 경제적 가치, 미래에 돈/이익으로 바꿀 수 있는 자원 | "내가 가진 것" |
| **부채 (Liability)** | 외부에 갚아야 할 의무, 미래에 자원이 나갈 약속 | "빌린 것" |
| **자본 (Equity)** | 자산에서 부채를 뺀, 진짜 내 몫 | "남는 내 것" |

세 항목의 관계가 곧 **회계 등식(accounting equation)**:

> **자산 = 부채 + 자본**

자본은 정의상 "자산 − 부채"이므로 등식이 깨질 수 없다 (그저 좌우 변형).

#### 가계 비유

5억짜리 아파트가 있고 그중 3억이 은행 대출이라면:

```
   자산   =   부채   +   자본
   5억    =   3억    +    2억
  (아파트)   (대출)     (진짜 순자산)
```

### 흐름 둘: 수익·비용

수익과 비용은 자산·부채·자본처럼 잔액으로 쌓이는 항목이 아니라, **자본이 늘고 주는 흐름**이다. 한 회계 기간(월/분기 등) 동안 누적되다가 마감 시점에 이익잉여금(자본)으로 대체된다.

| 종류 | 정의 | 자본 효과 |
|---|---|---|
| **수익 (Revenue)** | 영업으로 번 돈 | 자본 ↑ |
| **비용 (Expense)** | 영업을 위해 쓴 돈 | 자본 ↓ |

### 은행 회계 관점 + 함정

은행은 일반 회사와 자산/부채 구성이 꽤 다르다.

| 종류 | 은행의 대표 항목 |
|---|---|
| **자산** | 현금(금고), 대출채권(고객에게 빌려준 돈), 보유 채권 |
| **부채** | 고객 예수금(맡긴 돈, 언제든 돌려줘야 함), 차입금 |
| **자본** | 자본금(주주 출자), 이익잉여금(누적 이익) |

> **함정**: 고객 입장에선 통장 잔액이 자기 자산이지만, **은행 입장에선 부채**다. 고객한테 언제든 돌려줘야 할 빚이기 때문. 이게 본 시스템의 `201 고객예금` 계정이 부채로 분류되는 이유.

### 우리 프로젝트의 계정 분류

본 프로젝트가 쓰는 4개 계정코드를 위 분류로 매핑하면:

| 코드 | 이름 | 분류 |
|---|---|---|
| 101 | 현금 | 자산 |
| 201 | 고객예금 | 부채 |
| 401 | 수수료수익 | 수익 (→자본↑) |
| 501 | 이체대기 | 자산 (단순화 — 실무에선 미수금/미지급금으로 분리) |

## 차변·대변 규칙

장부의 좌우 자체는 의미가 없고, 위 다섯 계정 종류와 결합되어야 규칙이 결정된다.

### 왜 그런 자리가 되는가 — B/S 좌우 구조

회계 등식 `자산 = 부채 + 자본`이 그대로 대차대조표(B/S)의 좌우 구조다.

```
   ┌─────────────┬─────────────────┐
   │    자산     │   부채  +  자본 │
   │  (차변 쪽)  │     (대변 쪽)   │
   └─────────────┴─────────────────┘
```

각 계정 종류의 **기본 자리(home side)** 가 여기서 따라 나온다:

- 자산은 좌측에 사니까 → **증가 시 차변** (자기 자리로 들어감), 감소 시 대변
- 부채/자본은 우측에 사니까 → **증가 시 대변**, 감소 시 차변
- 수익은 자본 증가의 흐름이니 → **발생 시 대변** (자본 자리)
- 비용은 자본 감소의 흐름이니 → **발생 시 차변** (자본의 반대 자리)

### 5가지 계정 종류 전체 표

| 계정 종류 | 증가 시 | 감소 시 |
|---|---|---|
| **자산** (현금, 대출채권 등) | 차변 | 대변 |
| **부채** (고객예금, 차입금 등) | 대변 | 차변 |
| **자본** (이익잉여금 등) | 대변 | 차변 |
| **수익** (수수료수익 등) | — | 대변 |
| **비용** (인건비 등) | 차변 | — |

자산과 부채가 정반대라는 점이 핵심. 본 프로젝트가 다루는 5종 거래도 결국 이 표의 조합이다.

### 한 거래가 두 계정에 동시에 영향을 줄 수 있다

복식부기는 모든 거래가 차변·대변 양쪽에 1행씩 들어가야 하므로, 한 거래로 자산·부채·자본·수익 중 **두 곳 이상에 변동**이 일어난다. 예시:

- **DEPOSIT 50,000**: 자산(현금)↑ 50,000 + 부채(고객예금)↑ 50,000 — 등식 양변이 같이 증가
- **WITHDRAWAL 50,000**: 부채(고객예금)↓ 50,000 + 자산(현금)↓ 50,000 — 양변이 같이 감소
- **FEE 1,000**: 부채(고객예금)↓ 1,000 + 수익(수수료수익)↑ 1,000 = 자본↑ 1,000 — 자산은 그대로, 부채에서 자본으로 옮겨간 효과

세 케이스 모두 등식이 깨지지 않는다 (복식부기가 보장).

## 한 거래가 시스템에서 변환되는 흐름

예: 홍길동(110-123-000001)이 ATM에서 5만원 출금.

```
[1단계 — 운영 시스템 (실시간)]
   transactions 테이블에 1행 추가:
     account=110-123-000001, type=WITHDRAWAL, amount=50000, status=COMPLETED

[2단계 — 일일 거래 집계 배치 (Job 1, 새벽)]
   같은 계좌의 그 날 모든 거래를 합산:
     daily_transaction_summaries: account=110-123-000001, date=2026-05-05,
       total_deposit=300000, total_withdrawal=550000, ...

[3단계 — 분개 생성 배치 (Job 2, Job 1 직후)]
   거래를 은행 회계 관점으로 차변·대변 양쪽에 기록:
     출금 50000원 거래 →
       1) 고객 통장 잔액 ↓ → 부채(고객예금) 감소 → 차변 50000
       2) 금고 현금 ↓     → 자산(현금) 감소     → 대변 50000

       journal_entry: DEBIT  201 고객예금 50000
       journal_entry: CREDIT 101 현금     50000
   (차변·대변 각각 1행, 합 50000 = 50000 — 복식부기 invariant 충족)

[4단계 — 월별 마감 배치 (Job 3, 매월 1일)]
   한 달치 일일 summary를 다시 합산. 월간 손익/잔액 보고서 토대.
```

## 이 프로젝트가 다루는 범위

본 프로젝트는 위 흐름의 **2~4단계**를 Spring Batch로 자동화한다.

- **Job 1: DailyTransactionAggregationJob** — 일일 거래 집계 (구현 완료, Sprint 01)
- **Job 2: JournalEntryGenerationJob** — 분개 자동 생성 (Sprint 02)
- **Job 3: MonthlyClosingJob** — 월별 마감 (Sprint 03)
- 이들을 매일/매월 자동 트리거하는 **Scheduler** (Sprint 04)

1단계(거래 발생 자체)는 별도의 OLTP 시스템이며, 본 프로젝트에서는 `DataSeeder`로 시뮬레이션한다 (계좌 100개 × 일 1000건 × 7일).

## 의도적으로 다루지 않는 것

이 프로젝트는 학습/포트폴리오 목적이라, 실제 은행 시스템에서 중요하지만 시간 비용이 큰 다음 영역은 의도적으로 단순화/제외했다:

- **잔액 추적**: 일별 opening/closing balance 컬럼은 초기 설계 후 드랍됐다. 정확한 추적은 별도의 일별 잔액 스냅샷 테이블이 필요하며, 이는 정산 집계의 책임 영역이 아니다.
- **거래 카테고리(차변/대변 매핑) 외부화**: Job 2에서 type → 계정코드 매핑을 코드 내부에 둔다. 실제로는 회계 매핑 룰 테이블에서 동적 조회한다.
- **다국 통화/환율**: 모든 금액은 KRW 단일 통화 가정.
- **대사(reconciliation)**: 외부 시스템과의 잔액 일치 검증은 다루지 않는다.
- **승인/마감 워크플로**: 회계팀의 수동 검토/승인 절차 없이 자동 완료.
